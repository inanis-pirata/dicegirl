# TRPG 骰子机器人核心项目：AI 代码生成设计规格书

> **用途：** 将本文作为上下文提供给代码生成 AI，让 AI 按约束分阶段创建项目、实现代码、运行测试并维护架构一致性。  
> **技术方向：** Go + YAML + 本地文件存储 + 跨平台 + CoC 7 版首个规则包。

## 1. 项目概述

项目名称暂定为 `trpg-dicebot-core`。它是一个本地运行、跨平台、与聊天平台解耦的 TRPG 骰子与规则引擎。

第一阶段优先完成可独立运行的命令行程序和可复用的 Go 核心库；未来可以在其上增加 Discord、Telegram、QQ、Web 或其他适配器，但当前版本不实现平台接入。

首个规则系统以 CoC 7 版为例。架构必须允许未来增加 D&D 5e 或自定义规则包，而不需要修改通用骰子引擎。

## 2. 已确定的技术决策

- **语言：** Go，使用当前稳定版；在 `go.mod` 中明确 Go 版本。
- **配置与数据格式：** YAML。优先使用成熟、维护活跃的 YAML v3 实现。
- **存储：** 本地文件系统；角色卡、游戏存档和规则配置以明确约定的文件格式保存。
- **数据库：** 不使用 SQLite，不引入数据库服务。
- **部署：** Windows、Linux、macOS 可构建运行；避免不必要的平台专属依赖。
- **架构：** 通用骰子引擎与具体规则系统分离；规则数据与规则行为分离。
- **插件：** 第一版采用编译时注册的规则系统，不实现动态插件加载。
- **平台接入：** 第一版不实现聊天平台 SDK、机器人登录、消息收发或网络服务。
- **优先级：** 先保证核心逻辑正确、接口稳定、测试充分，再扩展功能。

## 3. 项目目标与非目标

### 3.1 目标

- 提供可复用、可测试的骰子表达式解析与执行引擎。
- 提供规则系统注册、发现、初始化和调用机制。
- 实现 CoC 7 版的基础检定、奖励/惩罚骰、成功等级、伤害、理智检定和角色卡基础管理。
- 支持角色卡与游戏数据的本地持久化、校验、备份和版本迁移基础机制。
- 提供 CLI，方便开发、调试和后续平台适配器调用。
- 所有核心规则逻辑都有自动化测试；随机结果可以通过注入随机源进行可复现测试。

### 3.2 非目标

- 不实现任何聊天平台接入。
- 不使用 SQLite 或其他数据库。
- 不在第一版实现运行时动态 Go 插件。
- 不把所有规则逻辑都写成 YAML 表达式；复杂判定由 Go 代码实现。
- 不把骰子引擎与 CoC 的术语、数据结构或规则判断耦合在一起。
- 不以生成大量未测试代码为交付标准；可编译、可测试、行为正确优先。

## 4. 功能范围与优先级

### P0：通用骰子核心

- 基础骰：`d4`、`d6`、`d8`、`d10`、`d12`、`d20`、`d100` 等。
- 骰子表达式解析与计算，例如 `1d100`、`2d6+3`、`4d6kh3`（若采用此语法，必须定义并测试）。
- 支持加减乘除或明确限制运算范围；禁止未定义行为、整数溢出和无界资源消耗。
- 结构化返回每个骰子的明细、修正值、总值、表达式和错误信息。
- 注入随机源，生产环境使用适合游戏的随机源，测试使用可控随机源。
- 明确解析错误、非法表达式、超大骰子数量、超大面数、除零等错误。

### P1：规则系统框架与角色卡

- 规则系统 Manifest：ID、名称、版本、规则版本、描述和配置文件位置。
- Rule 接口与 Registry：注册、查询、初始化、重复 ID 检查。
- 角色卡创建、读取、更新、删除、复制、切换/选择、导入导出和数据校验。
- 角色卡数据包含 `schema_version`、规则系统 ID、角色 ID、名称、属性、技能及可扩展的额外数据。
- 文件保存采用临时文件写入后原子替换的策略；在平台差异无法保证时，文档化降级行为。
- 文件路径必须由程序生成或经过严格校验，禁止路径穿越。

### P2：CoC 7 版核心判定

- 技能/属性检定：普通成功、困难成功、极难成功、失败和大失败等等级。
- 奖励骰与惩罚骰：按 CoC 7 版规则处理个位骰与十位骰，明确 `00` 的语义。
- 技能值、属性值和目标值的边界校验。
- 检定结果需同时保留原始骰值、最终骰值、目标值、成功等级与解释文本。
- 对抗检定作为单独规则用例实现，并通过合法规则资料或明确的项目规则说明确认优先级。

### P3：CoC 扩展规则

- 伤害表达式与武器伤害计算。
- 理智检定及成功/失败后的理智损失。
- 角色派生属性：生命、魔法、理智、伤害加值、体格等，规则数据与计算逻辑分离。
- 角色状态和成长记录的基础数据结构。
- 战斗、闪避、疯狂、伤口恢复等功能按独立用例逐步实现，不与 P0/P1 混在一起。

### P4：团务与主持人辅助

- 游戏/团存档、调查员与游戏关系、场景、NPC 的基础模型。
- 随机表、宏、规则查询、暗骰、结果解释。
- 回合管理和复杂战斗流程放在核心规则稳定后实现。
- 权限与多用户隔离只有在引入实际使用场景时再设计；CLI 单用户模式不要虚构复杂权限系统。

## 5. 架构原则

1. 依赖方向由外向内：CLI/应用层依赖领域层；领域层不得依赖 CLI、文件系统或具体规则包。
2. `dice` 包只负责表达式、掷骰、明细和骰子级错误，不负责 CoC 成功等级。
3. 规则系统调用通用 Dice Roller；通用 Dice Roller 不导入任何规则系统包。
4. 存储层负责文件读写、校验入口、原子保存、备份和版本迁移；业务规则不直接拼接文件路径。
5. 领域层返回结构化结果；CLI 负责把结构化结果格式化为人类可读文本。
6. 错误应可判断、可测试、可定位；避免只返回字符串或静默忽略错误。
7. 不要为了抽象而抽象；接口必须对应明确边界和可替换依赖。

## 7. 核心接口与数据模型约束

### 7.1 通用骰子引擎

建议把解析、执行和随机源分离。表达式语法应在 README 中明确定义，不能只靠 AI 自行猜测。第一版可以从 `NdM`、加减常量开始，之后再添加保留最高/最低、爆骰等扩展。

```go
type Roller interface {
    Roll(ctx context.Context, expr string) (RollResult, error)
}

type RollResult struct {
    Expression string
    Dice       []DieResult
    Modifier   int
    Total      int
}

type DieResult struct {
    Count int
    Sides int
    Rolls []int
}
```

以上为接口方向示例，不要求逐字照抄；实现前应检查字段是否足以表示复合表达式。若表达式支持多个骰组、保留规则或嵌套运算，应使用 AST/分组结果，避免用一个 `Dice` 数组和单一 `Modifier` 丢失信息。

### 7.2 规则系统

```go
type RuleSystem interface {
    Manifest() Manifest
    ValidateConfig(config any) error
}

type Registry interface {
    Register(system RuleSystem) error
    Get(id string) (RuleSystem, bool)
    List() []Manifest
}
```

如果使用泛型或配置类型，优先保证调用端类型安全。不要通过 `map[string]any` 承载所有核心业务数据；map 仅用于扩展字段或外部 YAML 解码边界。Registry 应检测空 ID、重复 ID 和无效版本。

### 7.3 角色卡

```go
type Character struct {
    SchemaVersion string            `yaml:"schema_version"`
    ID            string            `yaml:"id"`
    Name          string            `yaml:"name"`
    SystemID      string            `yaml:"system_id"`
    Attributes    map[string]int    `yaml:"attributes"`
    Skills        map[string]int    `yaml:"skills"`
    Metadata      map[string]string `yaml:"metadata,omitempty"`
}
```

该模型仅是最小示例。最终字段应由 CoC 角色数据需求驱动，并为 `schema_version` 定义迁移策略。角色卡文件名不得直接信任用户输入；ID 应由程序生成或严格校验。

### 7.4 结果与状态变更

- 骰子结果、规则判定结果、角色状态变更必须是不同层次的数据。
- 规则判定返回成功等级、目标值、骰值、解释和可选的状态变更建议。
- 计算阶段不要悄悄写回角色卡；由应用服务明确决定是否应用变更并保存。
- 同一次规则操作应能在测试中独立运行，不依赖全局变量或隐式文件读写。

## 8. YAML 配置与数据格式

### 8.1 Manifest 示例

```yaml
schema_version: "1"
id: "coc7"
name: "Call of Cthulhu 7th Edition"
system_version: "0.1.0"
rules_version: "7e"
description: "CoC 7e ruleset"
config:
  defaults: "defaults.yaml"
  skills: "skills.yaml"
```

### 8.2 配置设计规则

- YAML 只存放适合数据驱动的内容：技能清单、默认属性、武器伤害、派生属性参数和规则选项。
- 复杂流程和条件分支使用有测试的 Go 代码，不允许通过 `eval` 执行 YAML 中的代码。
- 所有配置加载后必须校验必填字段、数值范围、重复键语义和引用关系。
- 未知字段策略要明确：配置文件可选择严格拒绝，或通过显式扩展区承载；不要无意中静默吞字段。
- 规则配置、角色数据和游戏存档分别使用不同 `schema_version`，避免一个版本号承担所有迁移职责。
- 错误信息应包含文件路径、字段路径和原因，但避免输出敏感或无关内容。

## 9. 文件存储要求

- 默认数据根目录可配置；相对路径的解析规则在文档中固定。
- 角色卡使用稳定 ID 命名，不直接把角色显示名当路径。
- 保存步骤：序列化到同目录临时文件、Flush/Close、按平台支持情况原子替换；检查每一步错误。
- 更新文件前可创建带时间戳的备份；备份数量或清理策略应可配置，不能无限增长。
- 读取时区分文件不存在、权限不足、YAML 解析失败、schema 不兼容和数据校验失败。
- 防止路径穿越、符号链接相关风险和意外覆盖其他文件。
- 至少为存储层编写临时目录测试；测试不得污染真实用户数据目录。

## 10. 错误处理与日志

- 定义稳定的错误类别/错误码，例如：`INVALID_ARGUMENT`、`PARSE_ERROR`、`ROLL_ERROR`、`RULE_NOT_FOUND`、`VALIDATION_ERROR`、`NOT_FOUND`、`STORAGE_READ_FAILED`、`STORAGE_WRITE_FAILED`、`UNSUPPORTED_SCHEMA_VERSION`。
- 错误码用于机器判断，错误消息用于人类阅读；不要通过解析错误字符串决定程序流程。
- Go 代码使用 error wrapping（`fmt.Errorf` 的 `%w`）保留根因；对外输出时隐藏内部堆栈和无关路径细节。
- 日志至少区分 DEBUG/INFO/WARN/ERROR；核心库尽量不强制绑定具体日志框架。
- CLI 的错误输出应简洁、可操作；测试应断言错误类别，而不是依赖易变的整段文本。
- 错误码应集中定义并有文档；不要让每个包随意发明冲突编号。

## 11. CLI 命令草案

```bash
dicebot roll "1d100"
dicebot roll "2d6+3"
dicebot systems list
dicebot character create --system coc7 --name "Investigator A"
dicebot character show <character-id>
dicebot character list
dicebot character validate <character-id>
dicebot coc7 check --character <character-id> --skill psychology
dicebot coc7 sanity --character <character-id> --loss "1d4"
dicebot coc7 damage --expr "1d6+1"
dicebot config validate --system coc7
```

CLI 的命令名与参数可以调整，但要保持一致、可脚本调用，并区分标准输出与错误输出。核心逻辑不得只存在于 CLI handler 中。

## 12. 测试与质量门槛

- 每个包包含单元测试；重要规则覆盖成功、失败、边界、非法输入和异常路径。
- 骰子测试使用注入的可控随机源，不能依赖真实随机结果断言固定值。
- 规则测试应覆盖 CoC 7 版成功等级边界、奖励/惩罚骰、`00`/`0` 的解释和属性边界。
- 存储测试使用 `t.TempDir()`，覆盖创建、读取、更新、删除、损坏 YAML、权限/写入失败可模拟场景、版本不兼容。
- 集成测试验证 CLI 调用到应用服务和存储的关键流程。
- 每个阶段至少运行 `gofmt`、`go vet ./...`、`go test ./...`；有条件时运行 `go test -race ./...`。
- 不允许以跳过测试、注释掉失败断言或硬编码测试期望来掩盖缺陷。
- 任何新增依赖都要说明用途；优先标准库，避免为简单功能引入大型框架。

## 13. 编码规范

- 包名使用简短、小写、单词式名称；避免 `utils`、`common`、`base` 等无限扩张的包。
- 导出标识符使用 PascalCase，未导出标识符使用 camelCase；不使用匈牙利命名法或 `m_`、`str` 等前缀。
- 文件名使用小写下划线风格，测试文件以 `_test.go` 结尾。
- 函数应短小且职责明确；避免过度泛型、过度接口化和全局可变状态。
- 公开 API 必须有 Go doc 注释；关键规则算法需要注释说明规则依据和边界行为。
- `context.Context` 应传递给可能被取消或耗时的应用操作，不要随意存储在结构体中。
- 每次提交阶段性代码后更新 README、配置示例和测试说明。

## 14. 分阶段生成计划

1. **阶段 A：项目骨架。** 建立项目骨架、`go.mod`、CLI 入口、配置加载框架、错误类型、README 和最小测试；确保 `go test ./...` 通过。
2. **阶段 B：骰子引擎。** 实现骰子表达式 AST/解析器、随机源、Roller、结构化结果和完整单元测试。
3. **阶段 C：规则注册框架。** 实现 `RuleSystem`、Manifest、Registry 与 YAML 配置校验。
4. **阶段 D：角色卡与存储。** 实现角色卡模型、文件存储、原子写入、备份、schema 校验和 CLI CRUD。
5. **阶段 E：CoC 7 版基础检定。** 实现基础检定、成功等级、奖励骰/惩罚骰，加入边界测试。
6. **阶段 F：CoC 扩展。** 实现伤害、理智、派生属性和角色状态的基础逻辑。
7. **阶段 G：团务辅助。** 实现游戏存档、随机表、宏等辅助功能；每个功能单独评审和测试。
8. **阶段 H：发布准备。** 进行跨平台构建、错误路径审查、文档整理和完整回归测试。

## 15. 交给代码生成 AI 的主提示词

复制下面的提示词作为 AI 的主任务说明。推荐先让 AI 只执行阶段 A；验收通过后，再逐阶段继续。

> 你是一名资深 Go 工程师和软件架构师。请根据以下项目规格，帮助我实现一个高质量、可维护、跨平台的 TRPG 骰子机器人核心项目。
>
> **项目目标**
>
> 构建一个独立于聊天平台的 TRPG 骰子与规则引擎，项目暂定名 `trpg-dicebot-core`。使用 Go、YAML 和本地文件系统，不使用 SQLite，不实现聊天平台接入。第一个规则系统是 CoC 7 版，但通用骰子引擎不得依赖 CoC。
>
> **架构硬约束**
>
> 1. 分离通用骰子引擎、规则系统、角色卡领域模型、应用服务、CLI 和文件存储。
> 2. 使用编译时注册的规则系统 Registry；第一版不做动态插件。
> 3. YAML 用于规则数据和配置；复杂业务规则用有测试的 Go 代码实现，不执行 YAML 中的代码。
> 4. 领域逻辑不得直接访问文件系统；存储通过明确的接口或应用层依赖注入提供。
> 5. 返回结构化结果和可判断的错误类型；不要仅返回自由文本。
> 6. 随机源必须可注入，测试不能依赖真实随机数的固定结果。
> 7. 角色卡、规则配置、游戏存档分别定义 `schema_version` 和迁移策略。
